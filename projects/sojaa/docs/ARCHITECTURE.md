# Architecture notes

One Node/TypeScript API (Express, plain `pg`) and one Next.js console, on Postgres 16. A modular monolith: the rules that matter (a guard is in one place at a time; a shift is billed once; a closed month never changes) are database constraints and transactions, not network calls or good manners.

## Tenancy
Every tenant table has `org_id`, row-level security **enabled and forced**, and one policy `org_id = current_org()`. The API connects as `sojaa_app` (NOSUPERUSER, NOBYPASSRLS, not the owner) and binds the tenant per transaction with `set_config('sojaa.org_id', ..., true)`. Migrations run as a separate owner role. `sojaa_protect()` does enable, force and policy for a new table in one call; `sojaa_append_only()` revokes UPDATE, DELETE and TRUNCATE. At startup `assertRlsIsEffective()` refuses to run in production if the role could bypass RLS or any `org_id` table is not forced, so a table a later migration forgets is caught on the next boot. Lookups that must work before a tenant is known are narrow `SECURITY DEFINER` functions returning ids and a hash only: sign-in by phone (`resolve_login`), a guard's own sign-in (`resolve_guard`), a client's private link (`resolve_portal`), Sojaa's own billing reference. `signup_requests` is exempt (it exists before any tenant) and points at the created firm as `provisioned_org_id`.

## Time
Every event's time is the server's `now()`. A request body cannot carry a time for an attendance event (a test sends three and checks they are ignored). The one place a person types a time is a supervisor correction, which is a *new* event (`override_in` / `override_out`) with a reason of at least five characters (a CHECK), the stated time bounded to 12 hours around the shift and not in the future; the original stays. Days are Nairobi days: day-range filters use `date::timestamp AT TIME ZONE 'Africa/Nairobi'` (a first version cast the date straight to timestamptz and shifted every range by three hours; a midnight-boundary test now pins it).

## The roster cannot double-book
`shifts` carries `EXCLUDE USING gist (guard_id WITH =, tstzrange(start_at, end_at) WITH &&) WHERE (guard_id IS NOT NULL AND status = 'scheduled')`. In front of it, every path that gives a guard a shift takes `pg_advisory_xact_lock('guard-roster:<id>')` so two simultaneous requests queue and the second gets a readable 409 instead of two transactions deadlocking inside the constraint (ten concurrent overlapping creates produced 500s before the lock; a test now requires exactly one winner and nine 409s). Deadlock and serialization failures that still escape are mapped to a retryable 409.

## Attendance
One check-in and one check-out per shift: partial unique indexes on `attendance_events (shift_id) WHERE kind = 'in'` / `'out'`. The service also locks the shift row `FOR UPDATE`, so thirty simultaneous taps give one 201 and twenty-nine clear 409s; a separate test inserts a duplicate straight into the table as the app role to prove the index itself refuses it (dropping the index makes that test fail). Events are append-only. Effective in/out for a shift is the latest override if there is one, else the original; the board computes it in one query (`ATTENDANCE_SQL`) and classifies in pure code (`ops/attendance.ts`).
Geofence (`ops/geo.ts`): haversine distance; `within` if inside the radius, `outside` only if outside even after granting the phone its own stated error, otherwise `unknown`; (0,0) and missing fixes are `unknown`. It flags, it never blocks.

## Patrols
Checkpoints carry a random token (printed as a QR; kept in plain text so it can be reprinted; rotating it kills the old one). A scan needs the guard checked in and not out, a token at the shift's own site, and is append-only. Rounds (`ops/patrol.ts`): a round is one visit to every active checkpoint; a repeat visit starts the next round and leaves the previous incomplete with what it missed; an ordered site flags out-of-order rounds.

## Payroll
`payroll/compute.ts` is one pure function per guard per month (proration by days employed, premiums, overtime, deductions, the minimum-wage test, flags); `payroll/deductions.ts` holds the table shapes and arithmetic. Tables are data a firm enters; **no rate is hard-coded as fact** (the illustrative set exists, is labelled unverified, and loads as *unconfirmed*; an unconfirmed table deducts nothing and the month cannot close). A run upserts payslips by (period, guard), so a payslip keeps its id and a printed link survives closing. Closing re-computes inside the same transaction, refuses unless every table is confirmed or not applicable, requires a written acknowledgement for blocking flags or shifts without a check-out, stores a snapshot (settings, tables, holidays, summary), and then `BEFORE` triggers on `pay_periods` and `payslips` refuse every later insert, update or delete, including by the table owner. A correction is an append-only `payroll_adjustments` row paid in an *open* later month.

## Invoicing
An invoice bills shifts with a check-in and a check-out, ended before now, not already billed, at the rate in force that day (post beats site; latest effective date wins; newest entry breaks ties). `client_invoice_shifts.shift_id` is UNIQUE: two simultaneous generations leave one invoice and no shift billed twice (a test runs six at once; dropping the key makes it fail). Generation also takes an advisory lock per (client, month). Everything money-shaped is append-only; a mistake is a credit note. Payments allocate oldest first; the excess is held on account and applied to the next invoice. Debtors and margin are computed from those facts; a guard's month of employer cost is split across clients by verified minutes, to the exact cent (largest remainder).

## Concurrency and scale notes (not load-tested)
Lists are server-paged with a hard page cap; the board, payroll run and margin read a day or a month in one query and aggregate in the application, which is fine for hundreds to low thousands of guards and has not been measured beyond the sample. Sample provisioning takes about seven seconds (hundreds of single-row inserts); acceptable for a one-off, not for a signup storm.

## Money in and out
Sojaa takes M-Pesa money in one place only: its own subscription, on its own shortcode, matched to the firm by account number, idempotent on the transaction id. It pays nobody.
